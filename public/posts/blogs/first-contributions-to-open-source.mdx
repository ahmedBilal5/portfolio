This blog is about how I was able to make my first real contribution to open-source by Allah's grace; followed by a few more. It is less about the contributions themselves, and more about the mindset it took me to finally make one. In particular, I was able to find and report some bugs/issues in the open-core MUI-X component `data-grid-pro`.

It so happened that one of my projects at Zones was using MUI as part of its UI Kit. In addition to MUI components, which are free of cost to use, this project was also using 2 of MUI-X advanced components: the `x-data-grid-pro` and `x-date-picker`. In particular, the `x-data-grid-pro` was being utilized heavily throughout the project to display bulk volumes of data. 

The `data-grid-pro`, however, was the default client-side version, which required all data to be fetched from the server and then displayed (*In truth, while it is possible to make an implementation with paginated data using the client-side grid, it has limitations*).

I was tasked with finding a solution to this heavy pre-fetching of data which caused substantial loading times for users (in order of minutes). Fortunately, MUI-X had just released its version 8 some months ago in which they introduced capabilities for server-side data, server-side tree data, and lazy-loading data. 

It occurred to me to be the best course of action to get our MUI version bumped up to 8 and then start replacing our grids with the new server-side grids one after another. One problem, however, that I did not Forsee or account for is for the v8 `data-grid-pro` component *itself* to have bugs; bugs serious enough to hold me back implementing it in our project.  
 
Looking at it in hindsight, it seems quite understandable that a newly launched set of advanced features in a complex UI component would have some unidentified issues. But at the time, It never crossed my mind that such could be so. Perhaps because somewhere deep down, I had an impression that a well-known and widely used library like MUI was surely free of any bugs.

So fast-forward to the time I found the first issue. It was 2 a.m. in the morning and I was going to be on leave from work for a week starting this day. So I was free of any immediate pressure and had been tinkering around with the server-side `data-grid-pro` in my project until I got stuck with a problem in the grid about which I felt quite sure was not in my hands. It suddenly struck my mind that I could confirm if this was a problem in the grid itself by forking a stack blitz demo from the documentation and replicating my use-case there. On normal workdays, I would not have taken the trouble, but since I had holidays ahead, I was relaxed and decided to see where this leads. I replicated my use-case in the stackblitz enviroment and Alhamdulillah! The issue was reproduced.

I immediately opened the github issues page for MUI-X, read the issue creation guidelines and began to create an issue. Took me about 20 minutes to notch it all down. Proofread it twice and pressed the submit button. An interesting first-time exercise was all it was at the time.
 
I was surprised and glad when the issue was readily acknowledged by the MUI team in less than a week's time. That was a big confidence booster and a relief in the sense that any future problems I faced that felt out of my hands could be reported and received actual feedback upon. Whereas previously, I was under the impression that If I found an issue in a library or package, I would have no choice but to seek some alternative way. Fortunately, MUI guarantees support to its pro customers, so that was not the case here.

Fast-Forward, and I have reported 4 more issues (a total of 5) on the same MUI component, as I continue to work on my task of server-integration. 4/5 were genuine issues that were accepted and fixed. I am attaching an AI generated summary of each issue:

## Issues Reported in MUI DataGrid Pro

### 1. `params.groupKeys` Becomes Undefined After Data Source Re-computation

**Issue #21006**

While working with server-side tree data, I discovered that when a memoized data source is re-created, the `params.groupKeys` value passed to `getRows()` becomes `undefined`. This breaks row fetching logic for expanded tree nodes and makes data source re-computation unreliable.

🔗 https://github.com/mui/mui-x/issues/21006


### 2. Incorrect Sibling Uniqueness Validation for Tree Data

**Issue #21263**

I reported a bug where DataGrid Pro throws the error *"values returned by `getGroupKey` for all the sibling rows should be unique"* even when duplicate keys exist on rows that are not siblings. The validation incorrectly treats non-sibling rows as siblings.

🔗 https://github.com/mui/mui-x/issues/21263

### 3. `getRowId` Does Not Work with Server-Side Tree Data

**Issue #21357**

This issue highlights that the `getRowId` prop is ignored when using server-side tree data. As a result, applications that rely on custom row identifiers cannot properly integrate with the tree data feature.

🔗 https://github.com/mui/mui-x/issues/21357

### 4. `fetchRows()` API Not Working in Lazy Loading Mode

**Issue #21722**

I found that the `fetchRows()` API does not behave as expected when DataGrid Pro is configured for lazy loading. The method fails to trigger row retrieval, limiting its usefulness for on-demand data fetching scenarios.

🔗 https://github.com/mui/mui-x/issues/21722

### 5. Clearing Stale Rows with Active Filtering/Sorting in Server-Side Tree Data

**Issue #21755**

This issue investigates how to properly clear previously loaded rows when `filterModel` or `sortModel` changes while using server-side tree data. Without clearing stale data, the grid can temporarily display outdated rows during refreshes.

🔗 https://github.com/mui/mui-x/issues/21755


### The Verdict
There is no verdict! Just that, never lose hope in a solution early. Keep trying and a way always opens by Allah's grace.
